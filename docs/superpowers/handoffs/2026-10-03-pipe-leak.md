# Handoff: TokenUsage leaks pipes until the Mac runs out of pipe memory

2026-10-03. Found from a Tinker session while chasing an Xcode build that hung. Nothing in this
repo has changed yet apart from this file.

## What happened

Every `xcodebuild` on the Mac started hanging at the same step, in every shell, including a plain
terminal pane. Xcode's build service (`SWBBuildService`) starts a probe,
`clang -v -E -dM -isysroot … -x c -c /dev/null`, which writes about 16 KB to stdout and 20 KB to
stderr. The clang process sat blocked writing into a full pipe. The build service sat idle,
waiting for it to exit. Running the same clang command directly finished instantly.

The cause was the Mac's pipe memory, not Xcode. macOS caps the kernel memory all pipes may use
together. A new pipe normally starts at 16 KB and grows to 64 KB. Once the cap is used up, new
pipes get a minimal buffer. On this Mac, a fresh pipe with no reader accepted **512 bytes** before
blocking. Any parent that drains one of a child's pipes before the other then deadlocks once the
child writes more than that. Xcode's probe is one such case.

TokenUsage was holding most of that memory.

## Evidence (measured 2026-10-03, TokenUsage 0.1.3, PID 8031, up 6 days 9 hours)

- `lsof -n | awk '$5=="PIPE"'`: **2,824** pipe ends open on the whole Mac, **2,159** of them in
  TokenUsage. The next biggest holder was all `node` processes together, with 290.
- Of TokenUsage's pipe ends, **2,142 have no peer**: the other end is already closed, because the
  child that held it exited long ago. Only 24 have a live peer.
- TokenUsage had **8 orphaned `codex app-server` children**, each alive for more than 2 days
  (`pgrep -P <pid>`). Those 8 hold the 24 live pipe ends (three each: stdin, stdout, stderr).
- `UsageViewModel` refreshes every 60 s (`App/UsageViewModel.swift:93`). Every refresh runs
  `CodexAppServerClient.fetch`, and `ClaudeAccountLocator.runListing` runs whenever accounts are
  listed. So the leak grows with time awake: about 2,100 dead pipe ends in 6 days.
- Fresh-pipe test: a Python `os.pipe()` with a non-blocking writer accepted only 512 bytes before
  `EAGAIN`.

Reproduce the count yourself:

```sh
pid=$(pgrep -x TokenUsage)
lsof -n -p "$pid" | awk '$5=="PIPE"{ if ($NF ~ /^->/) live++; else dead++ } END {print "live", live, "dead", dead}'
pgrep -P "$pid" -l          # orphaned codex app-server children
```

Run it, wait a few refresh cycles (minutes), and run it again. The dead count should climb.

## Where it comes from (suspects, not yet confirmed by a test)

Three places start a child with `Pipe()`s. None of them closes every handle it creates:

1. **`CodexAppServerClient.fetch`** (`Sources/TokenUsageCore/IO/CodexAppServerClient.swift:43-74`).
   This is the strongest suspect, because it runs on every refresh.
   - `standardError = Pipe()`: never read and never closed. Both ends live as long as the `Pipe`
     object does.
   - `output.fileHandleForReading` is read with `availableData` but never closed.
   - `input.fileHandleForWriting` is closed, but the input pipe's read end is never closed.
   - After reading, it calls `process.terminate()` and never `waitUntilExit()`. So nothing reaps
     the child or confirms it died. `codex app-server` doesn't always exit on SIGTERM: the 8
     orphans prove some survive it. Nothing escalates to SIGKILL.
2. **`ClaudeAccountLocator.runListing`** (`Sources/TokenUsageCore/IO/ClaudeAccountLocator.swift:131-160`).
   It reads stdout to EOF and waits, but its `standardError = Pipe()` is never read or closed, and
   neither is the stdout read handle.
3. **`KeychainCredentials.readKeychainData`** (`Sources/TokenUsageCore/IO/KeychainCredentials.swift:66-89`).
   stderr already goes to `FileHandle.nullDevice`, which is right, but the stdout read handle is
   never closed. It runs less often (credentials are cached per account), so it's the smallest
   contributor.

Foundation's `Pipe` handles are supposed to close their descriptors when the handles are
deallocated. Two things prevent that: a `Process` that is never reaped, and a closure that still
holds the pipe. The orphaned children and the 2,142 dead ends show it isn't happening here. Don't
rely on deallocation. Close explicitly.

## Fix directions

- **Close every handle you create, explicitly, on every path**, including throws and timeouts:
  each `Pipe`'s `fileHandleForReading` and `fileHandleForWriting`, once the child has exited.
  `defer` blocks right after `process.run()` are the simplest way.
- **Don't give a child a `Pipe()` for a stream you never read.** Use `FileHandle.nullDevice` for
  stderr in `CodexAppServerClient` and `ClaudeAccountLocator`, as `KeychainCredentials` already
  does. That removes one leaked pipe per call outright. It also stops a chatty child from
  blocking on a full stderr, which the leak now makes far more likely.
- **Reap the codex child.** After `terminate()`, wait a bounded time (`waitUntilExit` on a
  background queue, or a termination handler with a semaphore). If it's still running, send
  SIGKILL (`kill(process.processIdentifier, SIGKILL)`), then wait. A `Process` that is never
  waited on keeps its pipes and leaves an orphan.
- **Consider one long-lived `codex app-server`** instead of a new one every 60 s. It speaks
  JSON-RPC over stdio and can answer `account/rateLimits/read` repeatedly. That avoids 1,440
  spawns a day, but it's a bigger change. The three fixes above stop the leak on their own.
- **Read both stdout and stderr concurrently**, or not at all, for any child that may write more
  than a few hundred bytes to both. Draining one stream to EOF before the other is exactly the
  deadlock that hung Xcode once pipes shrank.

## How to test it

A unit test can count this process's open descriptors before and after N calls. List
`/dev/fd`, or call `proc_pidinfo(getpid(), PROC_PIDLISTFDS, …)` and count `PROX_FDTYPE_PIPE`.
Point the clients at a fake binary: a shell script that prints a canned JSON-RPC response, and
one that ignores SIGTERM. Then assert:

- the pipe count is unchanged after, say, 20 fetches;
- the fake child that ignores SIGTERM is gone after `fetch` returns (it got SIGKILL and was
  reaped);
- a timed-out fetch also leaves the count unchanged.

`CodexAppServerClient` and `ClaudeAccountLocator` find their binaries from fixed search paths
(`locateBinary`), so the test needs an injection point for the binary path. That seam is a small
change, and worth making.

## Until it's fixed

Quitting and reopening TokenUsage frees every leaked pipe at once. The orphaned
`codex app-server` processes don't exit with it, because they're reparented to launchd. Kill them
too (`pkill -f 'codex app-server'`, checking first that no Codex session of your own is using
one). On this Mac that clears the Xcode hang. The leak comes back over a few days of uptime.
